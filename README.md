# cti-voice-pipeline

客服中心電話錄音 → 逐字稿 → 結構化標籤 → 統計的地端批次管線。

**全程地端，不經任何雲端 API。** 辨識用 Docker 版 whisper.cpp（CUDA），
分析用本機 Ollama。設計前提是資料含病患對話，任何一個位元組都不得離開本機。

> ⚠️ **這是去識別化的程式碼版本。**
> 機構名稱、院區名稱已置換為佔位字串；錄音、逐字稿、分析結果、報表、
> 標籤體系（`labels.json`）、術語表（`glossary.json`）與 system prompt 樣板
> （`prompt_system.txt`）**都不在本 repo 內**。
> 詳見〈[這個 repo 有什麼、沒有什麼](#這個-repo-有什麼沒有什麼)〉。

**這個 repo 是拿來被挑毛病的。** 作者第一次做這種規模的資料清洗與貼標，
整條管線只跟 AI 助手討論過，沒有經驗豐富的人看過。
如果你只想看一件事，請直接跳到〈[想討論的問題](#想討論的問題)〉。

## 資料流

```
CTI/<院區>/<YYYYMMDD>/*.WAV          原始錄音（gsm_ms 8 kHz 單軌，唯讀）
   │
   │  run_month.py --month 202509 --clinic A院區
   ▼
_run_<月>_<院區>/
   00_raw/                 月份鏡像，硬連結，不佔額外空間
   02_normalized/          16k mono PCM（膨脹 16 倍，轉完即刪）
   04_transcript/          逐字稿 .txt + .json（含毫秒時間軸）
   05_analysis/calls/*.json   每通一份結構化標籤（斷點續跑的單位）
   05_analysis/results.json   彙整
   state/ledger.sqlite     辨識階段帳本
```

兩個階段都是 GPU-bound，且**都可以隨時 Ctrl-C**：辨識階段有 SQLite 帳本，
分析階段每通一個 JSON 檔，重跑只做沒做過的。一年份資料可以分好幾天跑完。

## 檔案

| 檔案 | 做什麼 |
|---|---|
| `run_month.py` | 單月單院區總控，串接兩階段，產生工作目錄與日誌 |
| `cti_whisper_batch.py` | 錄音 → 逐字稿。ffmpeg 正規化 + Docker whisper.cpp，SQLite 帳本 |
| `cti_llm_pipeline.py` | 逐字稿 → 結構化標籤。Ollama + JSON schema grammar |
| `stats_calls.py` | 只讀檔名與 WAV 檔頭的全量通話量統計，不動 GPU，可與批次並行 |
| `build_stats_xlsx.py` | 把 `stats_calls.py` 的 CSV 組成 xlsx |
| `scripts/run_batch_clinics.ps1` | 依序跑多院區（刻意不併行，避免 GPU 互搶） |
| `scripts/gpu_monitor.ps1` | 每 10 秒記錄 GPU 溫度／使用率／功耗 |
| `config/*.example.*` | 設定檔與 prompt 樣板的結構範本（實際內容未發布） |
| `決策記錄.md` | **已拍板的決定與理由。想挑毛病的話這份比程式碼有用。** |

`stats_calls.py` 直接 import `cti_whisper_batch.parse_meta()` 來判定通話方向 ——
共用同一套規則，不兩邊各寫一份。

## 跑起來需要什麼

- Python 3.10+
- Docker Desktop + NVIDIA Container Toolkit（`ghcr.io/ggml-org/whisper.cpp:main-cuda`）
- ffmpeg
- Ollama（本機 `127.0.0.1:11434`）
- whisper 模型 `ggml-large-v3.bin`，放在 `models/`
- `labels.json`、`glossary.json`、`prompt_system.txt` —— 從 `config/` 的對應範本複製到 repo 根目錄後填入自己的內容：

```bash
cp config/labels.example.json        labels.json
cp config/glossary.example.json      glossary.json
cp config/prompt_system.example.txt  prompt_system.txt
```

三者缺一都會在啟動時直接退出，不會安靜地跑出爛結果。

```bash
python run_month.py --month 202509 --clinic A院區            # 完整兩階段
python run_month.py --month 202509 --clinic A院區 --stage asr # 只跑辨識
python run_month.py --month 202509 --clinic A院區 --limit 30  # 小量驗證
python stats_calls.py --root CTI --workers 24                # 排期估算，不動 GPU
```

路徑可用環境變數覆寫，不必改程式：`CTI_SRC`、`CTI_OUT`、`CTI_MODELS`、`CTI_ORG_NAME`。

長批次請用獨立程序啟動，否則會隨終端機 session 結束被帶走。

## 幾個實測數字

以單一院區一個月的量（約 3,900 通、75 小時音訊）為基準：

| 項目 | 數字 |
|---|---|
| whisper large-v3 辨識 | 75.1 小時音訊 → 2.25 小時完成（約 33x 實時） |
| Qwen 分析 | 無競爭時 7.4–8.0 秒/通 |
| 分析階段 token 用量 | `total_token ≈ 3182 + 4.249 × 逐字稿字元數` |
| 錄音格式 | 5 萬檔全數為 gsm_ms / 8 kHz / 單軌 |

**批次執行期間不要插隊跑樣本。** 實測會把主批次從 2.3 秒/檔拖到 19.4 秒/檔。

## 三件值得先知道的坑

1. **whisper 的 `--prompt` 不是指令，是「前一段的逐字稿」。**
   下了 prompt 會讓語音內容少的通話「只吐出 prompt 文字」，整通逐字稿全毀，
   而且**不會報錯**。預設已關閉，理由寫在 `cti_whisper_batch.py` 的 `INITIAL_PROMPT` 註解。

2. **結構比說明有力。** 選填欄位會被整個省略；enum 值的字面比 prompt 註解更能
   左右模型選擇。要改行為先改 schema，不是先改 prompt。

3. **證據要求能擋捏造，擋不住錯誤歸類。** 要求「每個標籤都要有逐字稿依據」
   治好了逐字稿補寫，但治不好標籤亂標 —— 模型永遠找得到某句話指過去。
   兩者不是同一個病。

## 想討論的問題

**先講清楚我的位置：這是我第一次做這種規模的資料清洗 → 貼標 → 分析。**
整條管線是我跟 AI 助手來回討論疊出來的，沒有經過任何有經驗的資料工程師或
資料科學家看過。它跑得動、產出看起來合理 —— 但「跑得動」跟「做對了」是兩件事，
我分不出來哪些決定是常識、哪些是我們兩個一起想歪的。

所以我想要的不是稱讚，是**挑毛病**。以下四個方向，任何一個有意見都歡迎開 issue，
講重話沒關係。

**要看我的推理過程，讀 [`決策記錄.md`](決策記錄.md)** —— 每個決定的理由、
當時的實測依據、以及三個被自己推翻的假設都在裡面。那份比程式碼更能看出我哪裡想歪了。

### 1. 這條流程跟業界主流做法差多遠？

我是照「直覺 + AI 建議」拼出來的，沒有對照任何既有的參考架構。想知道：

- 音訊 → 逐字稿 → LLM 貼標 → 聚合，這個切法本身是不是標準做法？
- 業界做這件事時，有沒有我整段漏掉的階段？（資料驗證？特徵層？資料契約？）
- 「每通一個 JSON 檔當斷點續跑單位」這種土法煉鋼，在正式環境會不會是反模式？

### 2. 只跟 AI 討論，會有什麼盲點？

這是我最在意的一題。過程中 AI 給的建議我大多採納了，而我沒有能力判斷
它有沒有系統性地偏向某些解法、或迴避了某些我該知道的難題。

已知自己踩過的坑寫在上面〈三件值得先知道的坑〉，那些是**事後**才發現的。
我想知道的是：**以你的經驗，這類專案最常見的失敗模式是什麼？**
特別是那種「當下看起來一切正常、三個月後才爆炸」的。

### 3. 個資與倫理，我做得夠嗎？

資料是真實的病患與客服通話，含姓名、生日、電話、病歷資訊、症狀主訴。
目前的作法是：

- 全程地端，不經任何雲端 API（這是硬規則，不打算放寬）
- 產出報表刻意做成本機 HTML，不進任何可分享的服務
- 逐字稿只留底，不建全文索引、不開放查詢
- 有一支去識別化腳本，但只用在要外流的報表上
- 標籤裡有 `contains_personal_data` / `pii_types` 欄位，但目前只是記錄，沒有觸發任何處置

想請教：

- 這樣的保護程度，對照台灣個資法與醫療場域的實務，是不足、剛好、還是我搞錯重點了？
- **通話的另一端（病患）並不知道錄音會被 AI 分析。** 這件事在倫理上該怎麼處理？
  告知？同意？還是這在客服錄音的既有告知範圍內？
- 分析「客服應對可改善之處」這種欄位，算不算對員工的變相監控？
  我刻意寫了「只記錄客觀可改善之處，不要評價人員」，但這樣夠嗎？
- 有沒有我根本沒想到的風險面向？

### 4. 從 PoC 到實際上線，架構要怎麼改？

目前這套是 PoC：單機、手動觸發、檔案系統當資料庫、沒有排程、沒有監控、
沒有測試、失敗靠人看 log。

想要一個**實際上線的參考 pipeline** 長什麼樣子 —— 不需要很完整，
講「你會先補哪三件事」就很有幫助。目前自己想得到的缺口：

| 現況 | 想問的 |
|---|---|
| 產出散在檔案系統，靠目錄命名 | 該進 DB 嗎？什麼形態的 DB？ |
| 手動跑，跑完才知道結果 | 排程與失敗告警的最小可行做法？ |
| 沒有任何自動化測試 | 這種「輸出不確定」的管線要怎麼測？ |
| 模型換版＝舊資料不可比 | 業界怎麼處理模型版本與資料版本的對應？ |
| 單機單卡，一個院區跑 4 小時 | 要擴到全院區規模，先動哪裡？ |
